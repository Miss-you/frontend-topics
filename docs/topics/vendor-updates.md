# 同步与升级

## 单一来源，独立运行

共享组件的源代码和版本保存在本仓库。消费者通过显式配置选择接入，将一个版本复制到自己的静态目录。它在运行时只使用本地副本，保持自己的 API、页面内容与部署边界。

`packages/daily-ui/package.json` 是组件版本来源。消费者根目录的 `frontend-vendor.json` 声明 `schemaVersion: 1`、`bundle: "daily-ui"`、`destination: "public/vendor/daily-ui"` 和本仓库的 `source` URL；生成目录中的 `manifest.json` 记录来源、版本及文件摘要。当前白名单包含两个组件、匹配函数与声明、共享样式、独立检查器 `verify.mjs` 和 `LICENSE`；清单之外的文件不属于同步工具可静默接管的内容。

## 更新顺序

1. 修改源组件及行为测试，通过本仓库检查。
2. 为发布内容更新组件版本；同版本不能重新代表不同内容。
3. 在选定源码版本上预览所有消费者的变更。
4. 明确写入组件目录，再执行漂移检查。
5. 在每个受影响消费者运行集成验收，检查业务文案、API、URL/历史和引用行为。
6. review、核对公开资源、提交与推送；把验证结果写进该次复盘。

```sh
node scripts/sync.mjs --target ../reader-a --target ../reader-b --preview
node scripts/sync.mjs --target ../reader-a --target ../reader-b --write --version 1.0.1
node scripts/sync.mjs --target ../reader-a --target ../reader-b --check
```

`--version` 应替换为本次预期的源码版本。默认预览不修改目标；`--check` 检查版本和文件漂移，不能替代组件或消费者测试。

## 两种检查证明不同的事

消费者可以在自己的仓库运行：

```sh
npm run frontend:check
```

该命令使用 vendor 中的 `verify.mjs`，只读取消费者本地的 `manifest.json` 与白名单文件，核对版本格式、文件集合及摘要。它适合日常开发和消费者 CI，不依赖另一个源码检出目录。

在本仓库运行 `node scripts/sync.mjs --target ../reader-a --check`，还会将消费者副本与当前检出的源组件版本、内容进行对照，适合发布和升级时核验。来源 checkout 应由维护者明确选择并完成 review。

本地清单检查通过，只能说明文件与这份清单一致；它不能证明副本是最新版本，也不能证明手工同时改动的文件和清单仍对应已审阅的来源。来源对照检查也不自动证明远端提交、发布标签或浏览器资源已经更新。两者都不能替代行为测试。

## 必须停止的情况

已登记文件与原清单摘要不符、文件被删除、目录出现未知内容、路径逃逸或符号链接等情况需要先处理，不能静默覆盖。多个目标应先完成整体规划和验证，避免因为后一个目标的已知冲突先改了前一个。

不要直接修补 vendor 副本后继续升级。将有效改动迁回源组件，发布新的版本；需要恢复原副本时先通过消费者自己的版本控制审阅并恢复。同步脚本不负责修改业务适配器、依赖配置、数据库和凭据。

## 适用范围

这是一种适合少量独立消费者的轻量维护方式。消费者数量或版本兼容要求增长时，可以评估独立包分发；不将当前选择写成永远禁止其他分发方式的规则。

本地多目录写入不等同于跨仓库事务。验证全部目标后仍可能遇到文件系统故障或并发编辑，失败后应检查实际计划和清单再继续；不能把部分成功描述为所有消费者已经升级。
