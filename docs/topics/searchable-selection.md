# 可搜索选择器

## 问题与复现

当候选从几个增加到几十个，逐项翻找的成本明显增加。用虚构作者 `author_one`、`author_two` 和百个候选复现；同时保留零候选、单候选、无匹配三种情况。

## 原因

普通下拉框表达了已选值，但搜索需要额外表达输入草稿、候选集合、当前键盘候选和已确认值。把草稿直接写进筛选状态，会使每次输入都变成页面切换；取消也无法恢复原选择。

## 交互契约

- 输入只过滤本地候选，不读取正文、不修改已选值。
- 点击候选或回车确认真实候选后，才通知消费者更新内容。
- Esc、点击组件外部或焦点离开整个组件时取消草稿，恢复已确认值；再次打开能够重新搜索。
- 空匹配不能提交任意文本；清除操作始终能恢复全部候选的业务视图。
- 键盘、鼠标与触屏都能完成核心选择，并有可见的候选状态。

匹配函数按完整、前缀、包含、顺序子序列排序，同级保留确定顺序；忽略大小写与起始 `@`。它不是拼写纠错、中文拼音或远程全文搜索，不能因此承诺这些能力。

## 架构边界与建议

组件接受 DOM、选项、标签与确认回调。消费者决定空作者是否禁用输入、URL 指定但尚无内容的作者如何说明，以及确认后保留日期还是切换日期。组件不掌握业务 API，也不管理浏览器历史。

候选数增长后，应按真实规模验证可读性和选择成本。百个候选是本专题的测试规模示例，不是所有产品必须启用搜索的统一阈值。更大规模或远程候选需要重新评估加载策略。

## 验收与关联

验证大小写、片段、非连续字符、无匹配、取消后重搜、键盘确认和清除。记录输入期间的网络请求数；将组件确认与消费者页面变更分别断言。使用真实触控输入验证弹层及候选点选。
