# FAQ：滚动、搜索与导航

本页记录可复现机制。下面的“契约”是当前组件承诺；“建议”只在对应条件下适用。具体版本是否通过，由该版本的测试与复盘记录证明。

## 1. 为什么设置 sticky 后仍不能独立滚动？

**原因：** 吸顶定位与滚动容器是两个问题。检查列表是否具有受限的可用高度、正确的溢出处理和实际内容溢出。当前契约还要求边界滚动不传给正文。

**检验：** 将鼠标放在日期项及区域留白处实际滚动，对比两侧位置。参见 [独立滚动](independent-scrolling.md)。

## 2. 已经做了 overflow，为什么首次仍滚不动？

**原因：** 首批内容可能没有填满区域。当前日期导航只补到形成滚动或历史耗尽，不一次读取全部历史。只有一日时没有可滚动内容是正常状态，应显示历史结束，而不是编造日期。

**检验：** 分别使用零日、一日、初始短列表和更多历史。关联 [独立滚动](independent-scrolling.md)。

## 3. scroll 事件一定意味着用户想看更多吗？

**原因：** 不一定。扩大视口可能改变滚动上限，使位置被调整，从而触发滚动事件。把所有 scroll 都当加载意图，会导致 resize 读取历史。

**解决与检验：** 区分用户输入意图与布局变化；把列表停在底部附近再显著增高窗口，断言没有新请求。关联 [交互验收](verification.md)。

## 4. 搜索输入和已选值为什么要分开？

**原因：** 输入属于草稿。只有确认候选才改变业务筛选，否则 Esc 无法自然取消，输入过程也可能不断替换正文。

**检验：** 已选 `author_one` 后输入另一片段，按 Esc，再次输入并确认；分别断言已选值、正文、URL 与请求。关联 [可搜索选择器](searchable-selection.md)。

## 5. 为什么刷新时不能顺手清空游标？

**原因：** 清空最后成功的游标会破坏失败恢复。连续刷新时，后一轮还可能把这个空状态保存为恢复依据。

**解决与检验：** 用独立加载状态暂停操作，保留已提交导航。连续发起两次刷新，让最新一次失败，确认旧历史仍可续读。关联 [异步导航状态](async-navigation.md)。

## 6. 已有旧响应校验，为什么历史按钮仍会锁住？

**原因：** 正文与导航使用了不同状态，却被同一个提前返回条件控制。正文已经切换时，当前筛选的导航仍可能需要恢复。

**检验：** 延迟刷新、切换日期、完成正文、再释放刷新；既检查正文，也点击“更早日期”证明后续导航有效。关联 [异步导航状态](async-navigation.md)。

## 7. 零候选、一候选和百个候选都要同一种交互吗？

**原因：** 它们暴露的风险不同。零候选需要明确空态与可清除的已选值，一候选需要直接确认，百个候选需要检查检索、键盘定位和弹层滚动。

**建议：** 按预期规模选择输入形式，不设置一个脱离上下文的强制数量阈值。匹配函数的顺序子序列能力不代表拼写纠错或拼音搜索。关联 [可搜索选择器](searchable-selection.md)。

## 8. 两个页面很像，直接复制整页不是更快吗？

**原因：** 首次复制容易，后续复制可能覆盖业务 API、文案、浏览器历史、引用安全和空态策略。相同的通用交互不代表相同的业务生命周期。

**解决与检验：** 同步组件白名单和版本清单，消费者保留适配器；分别验收业务差异。共享组件测试不能证明所有消费者接入正确。关联 [同步与升级](vendor-updates.md)。

## 9. 把窗口改成手机宽度，为什么还不能声称触屏通过？

**原因：** 视口大小不会自动把鼠标输入变成触控输入。候选点选、软键盘、弹层定位和滚动需要对应输入环境的证据。

**检验：** 使用触控上下文和真实 tap/滑动，同时核对可视范围。仅有 Chromium 触控模拟也不能代替所有真实设备。关联 [交互验收](verification.md)。

## 10. Playwright 测量为什么得到 undefined？

**复现：** 将 `locator.evaluate('node => node.scrollTop')` 当作调用节点回调。字符串表达式可能只得到一个未调用的函数，无法支持预期测量；应传入实际函数。

项目未包含 DOM 类型时，可以在浏览器回调中采用明确的结构类型，而不是给整个项目增加 `any`：

```ts
const top = await locator.evaluate((node) => {
  const box = node as unknown as { scrollTop: number };
  return box.scrollTop;
});
```

**检验：** 先让真实滚动发生，再确认测量确实得到数值；不要只让类型检查与 lint 通过。测试工具本身也需要能失败的验证。关联 [交互验收](verification.md)。

## 11. 滚动位置没变，为什么键盘操作仍然中断？

**复现：** 聚焦已有日期链接，再滚动加载下一页；或让同一筛选范围的刷新失败。列表看起来位置未变，但继续用键盘时焦点已离开原日期。

**原因：** 追加历史时重建整个列表，会移除原先获得焦点的 DOM 节点。只恢复 `scrollTop` 或创建相同文字的新链接，不能保留那个节点。失败恢复也可能在“重新渲染旧数据”时重复这个问题。

**解决：** 以日期为稳定 key 保留仍存在的链接节点，仅插入、更新、移动或移除实际变化的项。同一筛选范围刷新失败时保留原节点；真正切换筛选或删除日期的焦点策略需另行设计。

**检验：** 先聚焦日期，再追加历史或触发同范围刷新失败，分别断言该日期仍被聚焦，并继续键盘导航。滚动位置断言和截图不能替代焦点断言。对应案例见 [组件端到端测试](../../tests/e2e/contracts.spec.js) 中的 `appending history preserves the focused date node` 和 `a failed same-scope refresh preserves the focused date`。这些键盘焦点检查不代表已完成所有辅助技术验收。

## 12. 本地 vendor 检查通过，为什么还要与来源版本对照？

**原因：** 本地检查只能证明当前文件符合当前清单。若文件与清单被一起手工修改，或者副本仍停留在旧版本，本地一致性不足以证明它来自本次审阅的源版本。

**解决与检验：** 消费者日常使用 `npm run frontend:check`；升级时在明确选定的来源 checkout 运行同步脚本的 `--check`，再运行消费者集成测试并核对实际资源。保留这几个不同层次的证据，不用一个绿色检查替代全部结论。关联 [同步与升级](vendor-updates.md)。

## 13. 工作区全绿，为什么还需要核对提交后的独立安装？

**复现场景：** 新增测试或适配器引用了另一份未提交的模块，本机目录中存在它，独立检出却缺少文件。

**原因：** 工作区、提交、依赖安装和公开运行分别是不同状态。一个状态下通过的结果不能自动推导另一个状态可复现。

**做法与约束：** 除业务验收外，检查新增 import 与生成资源的提交可达性；发布前从只含提交文件的检出中按锁文件独立安装并运行命令。准备目录和执行安装是操作步骤，只有对应代码和行为检查通过才构成验收证据。发现其他任务的依赖缺口应明确责任和关闭条件，不能静默混入未审查改动。

**边界：** 共享组件的独立验收不替代每个消费者的业务验收，消费者通过也不替代公开资源核对。关联 [交互验收](verification.md) 和 [复盘模板](../templates/retrospective.md)。
