# 交互验收

## 要证明什么

为每条交互契约写出可失败的观察。页面能显示、没有横向溢出和测试总数增加，都只能支持局部结论。

| 主张               | 必要观察                                                           |
| ------------------ | ------------------------------------------------------------------ |
| 日期独立滚动       | 对区域发送真实滚轮，比较左右滚动位置并覆盖两端边界                 |
| 搜索在本地完成     | 输入时请求数不变，确认后才发生消费者读取                           |
| 追加后仍可键盘导航 | 先聚焦日期，追加历史或触发同范围刷新失败后，检查活动元素仍是原节点 |
| 取消保留选择       | 候选变化后取消，正文、URL 和已选值均保持                           |
| 旧响应不会覆盖     | 控制响应顺序，释放旧请求后断言页面和后续导航仍正确                 |
| resize 不读取历史  | 将列表放到靠近底部，再显著扩大高度，观察请求数                     |
| 手机可以操作       | 触控上下文中的真实 tap/滑动与弹层边界，而不只是窄视口              |

## 最小覆盖矩阵

按变更选择数据与场景，不要求所有组件使用相同固定数量的测试：

- 数据：零项、一项、多项、百项候选；初始短历史与深历史。
- 状态：正常、加载中、无结果、失败可重试、历史耗尽。
- 输入：滚轮、键盘、鼠标和触控。
- 组合：刷新加选择、连续刷新、作者切换加历史迟到、浏览器前进/后退。
- 布局：宽桌面、中等宽度、窄手机，以及实际使用的断点两侧。

组件测试证明共享行为；消费者测试证明它与 API、页面内容、历史策略组合后仍成立。最终公开站点还需核对实际资源版本与关键交互。HTTP 200 本身不能证明部署了被测试的版本。

## 证据边界

测试数据必须与生产存储隔离。人工截图和独立 review 可以发现自动化未覆盖的问题，但不能写成产品自动执行的能力。保留复现场景比保存一次绿色测试数量更有复用价值。

当前仓库的浏览器验收以配置和实际运行结果为准；只运行 Chromium 时只声称 Chromium 已验证。其他引擎、辅助技术和未来浏览器变化继续保留为明确边界。
